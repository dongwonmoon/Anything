## 07.03
- 검색 기능 개발
	- 가능한 방안들
	- 1. 화면에 이미 올라온 기록만 필터: SQLite에서 전체 기록 불러옴 -> 검색어로 JS 배열 filter
		- 단순, DB 쿼리 X, MVP에 적합, 테스트도 쉬움
		- 기록이 많아지면 처음에 전체를 불러오는 비용이 있음, 정교한 검색/랭킹/초성 검색이 어려움, 
		  검색보다는 필터에 가까움
	- 2. 검색어가 바뀔 때 마다 SQLite에 질의
		- 기록이 많아져도 화면에 필요한 것만 가져올 수 있음. 나중에 페이지네이션/정렬과 붙이기 좋음
		- repository API 추가 필요, SQL 검색 조건 설계 필요, 디바운스 필요, 검색 대상이 늘면 쿼리가 지저분함, 지금 규모에 비해 구조가 무거움
	- 3. SQLite FTS사용
		- 검색 품질/속도 면에서 가장 좋음. 긴 메모, 많은 기록에 강함. 하이라이트/랭킹/prefix 검색 등으로 확장 가능
		- FTS 테이블/동기화/마이그레이션 필요. 저장/수정/삭제 시 검색 인덱스도 맞춰야 함. 유지보수 비용 증가. 지금은 확실히 과함
	- 따라서, 1번으로 진행하되 추후 2번으로 전환한다. [[#Remind|↑ Remind]] ^record-search-strategy
- book_snapshot_json 분리 필요성의 점검 [[#Remind|↑ Remind]] ^book-table-separation
	- 같은 책의 기록을 안정적으로 모으고 싶을 때, 책 별 통계/필터가 중요해 질때, "내 책장"을 앱의 핵심 기능으로 만들 때, 책 정보를 수정하면 관련 기록에 일괄 반영하고 싶을 때, "읽는 중/읽음/인생 책/평점" 같은 책 자체의 상태가 생길 때
	- 지금 분리하면: SQLite migration 필요, 기존 데이터를 backfill, 같은 책 판별 규칙을 정해야 함, 기록 저장/수정/삭제 경계가 복잡해짐, "스냅샷으로 남길 것인가/책 테이블의 최신 값을 보여줄 것인가" 정책 결정 필요
	- 따라서, "책 별로 다시 보기를 만들 때": 첫 구현은 snapshot 기반 grouping으로 시작, 그때 불편하면 books 테이블 분리 검토.
	- "나의 서재/읽은 책/평점/책 정보 수정/책별 통계" 중 하나를 진짜 핵심 기능으로 만들기로 결정하면 분리
