## 1. 이번 달 완료한 것

### 기능

-  local-first 방향으로 제품 구조 전환
    
    - 기록, 사진, draft, 다시보기 상태를 기기 로컬 중심으로 이동
        
    - 서버는 사용자 기록/사진 저장소가 아니라 책 검색 프록시 중심으로 축소
        
-  로그인 없는 첫 실행 흐름으로 전환
    
    - 초기 local-first release에서는 login/signup/logout/account deletion UI를 숨김
        
    - login/signup route와 legacy auth code는 삭제하지 않고 dormant code로 보존
        
-  기록 저장소를 SQLite 기준으로 전환
    
    - completed record, book snapshot, photo metadata, resurface history를 SQLite에 저장
        
    - 사진 binary는 SQLite가 아니라 app-owned document storage에 저장
        
-  사진 lifecycle local-first 처리
    
    - draft 사진은 임시 자산으로 취급

    - 기록 삭제 시 DB 삭제를 우선하고, 사진 파일은 best-effort cleanup으로 처리
        
-  Home / 다시보기(resurface)를 local SQLite 기준으로 전환
    
-  active mobile flow에서 legacy server record fallback 제거
    
    - 기록 관련 server API wrapper 의존 제거
        
    - active screen은 local SQLite와 app-owned photo storage를 직접 사용

## 4. 결정 기록

### 결정. 서버가 사용자 기록/사진을 소유하지 않고 local-first로 간다

- 날짜: 2026-06-12
    
- 결정: reading records와 attached photos는 기본적으로 기기 안에 저장한다.
    
- 이유: 초기 release에서 서버가 auth, 기록, 사진, 복구, 계정 삭제까지 책임지는 것은 제품 가치에 비해 운영 표면이 너무 크다.
    
- 대안:
    
    - 기존 server-owned API를 먼저 배포
        
    - 서버 기록 + 로컬 사진 혼합
        
    - 백엔드 완전 제거
        
    - backup/sync 즉시 구현
        
- 다시 검토할 조건:
    
    - 사용자가 backup, restore, multi-device sync를 요구할 때
        
    - local storage 신뢰성/용량 문제가 측정될 때
        
    - 유료 기능, 공유 기능, 계정 기반 entitlement가 필요할 때
        

---

### 결정. 로그인은 삭제하지 않고 active UX에서 숨긴다

- 날짜: 2026-06-15
    
- 결정: 초기 local-first release에서는 login/signup/logout/account deletion UI를 숨긴다.
    
- 이유: 지금은 계정이 제공하는 사용자 가치가 없고, 로그인은 개인정보/계정 삭제/보안/운영 책임을 즉시 키운다.
    
- 대안:
    
    - 로그인 유지
        
    - 로그인 기능 완전 삭제
        
- 다시 검토할 조건:
    
    - backup/sync/community/paid feature가 active scope에 들어올 때
        

---

### 결정. SQLite를 primary local record store로 사용한다

- 날짜: 2026-06-12
    
- 결정: completed records, book snapshots, photo metadata, resurface history를 SQLite에 저장한다.
    
- 이유: 기록은 사진, 책 snapshot, 다시보기 이력과 관계를 가지므로 JSON 파일보다 관계형 local store가 적합하다.
    
- 대안:
    
    - FileSystem JSON
        
    - AsyncStorage
        
    - SecureStore
        
    - MMKV
        
    - Realm / WatermelonDB
        
- 다시 검토할 조건:
    
    - record volume이나 query pattern이 SQLite 한계를 드러낼 때
        
    - cloud sync가 conflict resolution 내장 저장소를 요구할 때
        
    - Expo SQLite가 release target을 막을 때
        

---

### 결정. 사진 binary는 SQLite가 아니라 app-owned document storage에 저장한다

- 날짜: 2026-06-13
    
- 결정: SQLite에는 photo metadata와 local file reference만 저장하고, 사진 binary는 app document storage에 저장한다.
    
- 이유: 사진 binary를 DB에 넣지 않고 파일로 관리하는 편이 local storage, cleanup, rendering 측면에서 더 적합하다.
    
- 대안:
    
    - SQLite BLOB 저장
        
    - 서버 photo upload 유지
        
    - 원본 사진 보관
        
- 다시 검토할 조건:
    
    - backup/sync를 설계할 때
        
    - 사진 품질/저장공간/cleanup 문제가 실제로 커질 때
        

---

### 결정. Cloudflare Workers를 thin API 1차 배포 타깃으로 사용한다

- 날짜: 2026-06-16
    
- 결정: 첫 사용자-facing thin API host는 Cloudflare Workers를 우선한다.
    
- 이유: 현재 backend는 `/health`와 Aladin book-search proxy 정도라 request-driven Worker와 잘 맞는다. DB, filesystem, background job이 필요 없다.
    
- 대안:
    
    - Oracle Free Tier VM
        
    - Render Free
        
    - Railway
        
    - Fly.io
        
    - Koyeb
        
    - Supabase Edge Functions
        
- 다시 검토할 조건:
    
    - Worker limit이 latency, bundle size, secret, logging을 막을 때
        
    - API가 book search와 health를 넘어 커질 때
        
    - Aladin quota 때문에 shared limiter/cache가 필요해질 때
        

---

### 결정. 검색 캐시는 지금 구현하지 않는다

- 날짜: 2026-06-15
    
- 결정: DB 기반 BookSearchCache, Redis, distributed rate limit, provider fallback은 지금 하지 않는다.
    
- 이유: 사용자도 없고, 서버 역할도 thin proxy로 줄었고, 모바일 화면 안에는 이미 같은 검색어 재검색 방지 메모리 캐시가 있다.
    
- 대안:
    
    - DB cache TTL 구현
        
    - Redis 기반 limiter
        
    - provider fallback
        
    - 고급 검색 normalization/ranking
        
- 다시 검토할 조건:
    
    - Aladin quota가 아까워질 때
        
    - 무료 quota를 자주 칠 때
        
    - 서버가 여러 대가 될 때
        
    - 검색 실패가 사용자 불만으로 드러날 때

- 다시 검토할 조건:
    
    - CI 시간이 병목이 될 때
        
    - release artifact 생성이 반복 작업이 될 때

- 결정: Play signing, AAB, 정책 문서보다 먼저 UI/UX release polish를 진행한다.
    
- 이유: 앱은 이미 dev-client 밖에서 실행되고, thin API와 preview APK evidence도 있다. 다음 리스크는 “작동하느냐”보다 “설명 없이 써도 신뢰감 있느냐”다.
    
- 대안:
    
    - Play signing 먼저 진행
        
    - AAB distribution 먼저 진행
        
    - release automation 먼저 진행
        
- 다시 검토할 조건:
    
    - 외부 tester build 배포 직전
        
    - closed testing 준비 단계 진입
        
    - UI polish가 release blocker를 더 이상 만들지 않을 때
