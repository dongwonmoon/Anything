	- (기존) /books/search를 유지하고, Aladin key 보호, rate limit, cache TTL, query normalization을 harden한다.
	- (의심) "cache TTL 구현"이 당장 필요한가? 사용자도 없고, 서버 역할도 줄이고 있고, 모바일 화면 안에는 이미 같은 검색어 재검색을 막는 메모리 캐시가 있다.
	- 하기로 한 것
		1. ALADIN API KEY가 클라이언트 쪽에 새지 않는지 확인
		2. rate limit은 MVP 보호장치로 유지 (예전에 구현했던 in-memory limiter. 단점이 많음)
		3. 모바일은 검색 실패를 로그인 문제로 해석하지 않는다. (local-first 전환 영향)
		4. DB BookSearchCache 흔적은 "지금 쓰지 않는 legacy/deferred 요소"로 분류
	- 안 하기로 한 것
		1. DB 기반 검색 캐시를 구현하지 않는다
		2. Redis, distributed rate limit, multi-instance quota sync 같은 운영 복잡도를 넣지 않는다
		3. 검색 랭킹, provider fallback, 고급 normalization을 하지 않는다.
	- 나중에 할 수 있는 것
		1. Aladin quota가 아까워지면 서버 캐시를 검토
		2. 무료 quota를 자주 치면, daily/user/IP limit을 검토
		3. 서버가 여러 대가 되면(... 서버는 프록시의 역할밖에 없긴 하지만...) in-memory rate limit이 의미 없어지므로 공유 저장소 기반 limiter을 검토
		4. 검색 실패가 사용자 불만으로 드러나면 provider 장애 메시지, 재시도 UX, 수동 입력 정책을 다시 본다.
