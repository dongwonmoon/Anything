## 한 줄 정의

> **이 상황을 어떤 문제로 볼 것인가?**

Problem Framing은 문제를 해결하기 전에, 지금 상황을 어떤 관점과 틀로 바라볼지 정하는 것이다.

같은 요청이라도 어떤 문제로 프레이밍하느냐에 따라 해결책이 완전히 달라질 수 있다.

---

## 언제 떠올릴까?

다음과 같은 상황에서 떠올리면 좋다.

- 사용자가 기능을 요청했을 때
    
- 요구사항을 분석할 때
    
- 기존 기능을 개선하려고 할 때
    
- 성능, 사용성, 운영 문제가 생겼을 때
    
- AI에게 작업을 시키기 전에
    
- “무엇을 만들지” 결정하기 전에
    
- 요청이 너무 넓거나 애매할 때
    
- 해결책은 보이지만 진짜 문제가 불분명할 때
    

중요한 점은, 표면적인 요청을 그대로 받아들이지 않고 그 요청이 나오게 된 배경을 생각하는 것이다.

즉, 사용자의 말을 바로 해결책으로 받아들이기보다,

> “이 사람이 왜 이런 요청을 했을까?”  
> “이 요청 뒤에 있는 진짜 불편은 무엇일까?”  
> “다른 방식으로 문제를 볼 수는 없을까?”

를 먼저 생각하는 태도에 가깝다.

---

## 이 개념을 모르면 생길 수 있는 문제

Problem Framing을 하지 않으면, 사용자가 말한 요청을 그대로 구현하게 될 수 있다.

그 결과 다음과 같은 문제가 생긴다.

- 문제의 근본 원인을 파악하지 못한다.
    
- 임시방편의 해결책만 만든다.
    
- 필요 없는 기능을 만들게 된다.
    
- 구현 비용이 큰 기능을 성급하게 만든다.
    
- 사용자는 여전히 불편함을 느낀다.
    
- AI가 사용자의 잘못된 프레임에 갇힌 채 코드를 만든다.
    
- 진짜 문제는 남아 있는데, 겉보기 기능만 늘어난다.
    
- 나중에 유지보수할 기능만 많아진다.
    

특히 AI 시대에는 더 중요하다.

AI는 내가 준 요청을 빠르게 구현할 수 있지만, 내가 문제를 잘못 정의하면 **잘못된 문제를 아주 빠르고 그럴듯하게 해결해버릴 수 있다.**

---

## 대표 질문

Problem Framing을 할 때는 다음 질문을 던져본다.

### 요청을 의심하는 질문

- 사용자가 말한 것은 문제인가, 해결책인가?
    
- 이 요청이 나오게 된 실제 불편은 무엇인가?
    
- 사용자가 정말 원하는 결과는 무엇인가?
    
- 이 기능이 없어서 문제인가, 아니면 다른 구조적 문제가 있는가?
    

### 다른 프레임을 찾는 질문

- 이 상황을 다른 문제로 볼 수는 없을까?
    
- 사용성 문제인가?
    
- 정보 구조 문제인가?
    
- 데이터 품질 문제인가?
    
- 운영 프로세스 문제인가?
    
- 성능 문제인가?
    
- 권한이나 보안 문제인가?
    
- 커뮤니케이션 문제인가?
    

### 해결책을 비교하는 질문

- 꼭 이 기능을 만들어야 해결되는가?
    
- 더 단순한 해결책은 없는가?
    
- 지금 만들면 비용이 너무 크지 않은가?
    
- 이 해결책이 진짜 문제를 해결하는가?
    
- 이 기능을 만들지 않고도 문제를 줄일 수 있는가?
    

### AI에게 작업시키기 전 질문

- 내가 AI에게 너무 좁은 문제를 준 것은 아닌가?
    
- AI가 내 요청에 매몰될 가능성은 없는가?
    
- 먼저 문제 정의를 시킨 뒤 구현을 맡겨야 하지 않을까?

## AI에게 시킬 프롬프트

```text
내 요청을 그대로 구현하지 마.

먼저 이 요청이 실제 문제인지,
아니면 내가 생각한 해결책인지 검토해줘.

다음 항목으로 나눠서 분석해줘.

1. 사용자가 말한 요청
2. 이 요청 뒤에 있을 수 있는 실제 문제
3. 가능한 문제 프레임
4. 각 프레임별 가능한 해결책
5. 가장 단순한 해결책
6. 지금 구현하면 위험한 점
7. 추가로 확인해야 할 질문
```

조금 더 강하게 요청할 때:

```text
내가 제시한 해결책에 동의하지 말고,
먼저 문제 정의가 잘못되었을 가능성을 검토해줘.

이 요청을 최소 5개의 다른 문제 프레임으로 다시 해석하고,
각 프레임마다 해결책이 어떻게 달라지는지 비교해줘.
```

실무적인 버전:

```text
사용자가 “OO 기능이 필요하다”고 요청했다.

바로 기능을 설계하지 말고,
이 요청 뒤에 숨어 있을 수 있는 실제 불편을 분석해줘.

다음 관점으로 나눠줘.

1. 사용자 경험 문제
2. 정보 구조 문제
3. 데이터 품질 문제
4. 운영 프로세스 문제
5. 성능 문제
6. 권한/보안 문제
7. 비용과 유지보수 문제

각 관점마다 가능한 해결책과,
가장 작은 1차 해결책을 제안해줘.
```

## 간단한 예시

### 예시 1. 검색 기능

사용자 요청:

> 검색 기능 만들어줘.

이 요청을 그대로 해석하면 다음과 같이 볼 수 있다.

> “우리 서비스에는 검색 기능이 없어서 사용자들이 불편하구나.”  
> “그러니 검색 기능을 만들면 되겠구나.”

하지만 다르게 프레이밍할 수도 있다.

> “사용자가 원하는 정보를 빠르게 찾지 못하고 있다.”  
> “정보 구조가 정리되어 있지 않다.”  
> “목록이 너무 많아서 탐색 부담이 크다.”  
> “사용자가 시스템에서 쓰는 용어를 잘 모른다.”  
> “데이터 제목이나 카테고리 품질이 낮다.”

프레임이 달라지면 해결책도 달라진다.

|문제 프레임|가능한 해결책|
|---|---|
|검색 기능이 없다|검색창 추가|
|원하는 정보를 못 찾는다|검색, 필터, 정렬, 추천, 카테고리 개선|
|정보 구조가 엉켜 있다|카테고리 재설계|
|목록이 너무 많다|필터, 태그, 인기순 정렬, 기본 정렬 개선|
|사용자가 용어를 모른다|자동완성, 추천 검색어, 안내 문구|
|데이터 품질이 낮다|제목 규칙, 태그 규칙, 입력 가이드 개선|
|자주 찾는 항목이 반복된다|즐겨찾기, 최근 본 항목, 바로가기|

따라서 “검색 기능”을 바로 만드는 것이 항상 정답은 아니다.

진짜 문제는 검색 기능이 없는 것이 아니라, 사용자가 원하는 정보를 찾기 어려운 구조일 수 있다.

---

### 예시 2. 관리자 페이지

사용자 요청:

> 관리자 페이지가 필요해요.

이 요청을 그대로 해석하면 다음과 같이 볼 수 있다.

> “관리자 페이지가 없어서 문제구나.”  
> “관리자가 데이터를 관리할 수 있는 화면을 만들면 되겠구나.”

하지만 실제 문제는 여러 가지일 수 있다.

|가능한 문제 프레임|가능한 해결책|
|---|---|
|악성 게시글을 처리할 수 없다|게시글 숨김, 신고 검토, 제재 기능|
|카테고리가 잘못 분류된다|카테고리 수정 기능, 입력 가이드|
|공지나 배너를 직접 바꾸고 싶다|CMS 기능|
|사용자 문의 대응이 어렵다|사용자 조회, 상태 확인 기능|
|DB를 직접 수정하는 것이 위험하다|안전한 내부 운영 도구|
|누가 무엇을 바꿨는지 모른다|감사 로그|
|운영 현황을 알고 싶다|통계 대시보드|
|권한을 나눠야 한다|관리자 권한 관리|

이 경우 바로 거대한 관리자 페이지를 만들기보다, 먼저 질문해야 한다.

> 관리자는 정확히 무엇을 하려고 하는가?  
> 조회가 필요한가, 수정이 필요한가, 삭제가 필요한가?  
> 실수했을 때 되돌릴 수 있어야 하는가?  
> 누가 어떤 권한을 가져야 하는가?  
> 기록이 남아야 하는가?

|관련 개념|관계|
|---|---|
|Root Cause Analysis|문제의 근본 원인을 찾는 과정|
|5 Whys|왜 그런지 반복해서 파고드는 방법|
|Jobs To Be Done|사용자가 진짜 하려는 일을 파악하는 관점|
|User Journey|사용자의 실제 흐름을 따라가며 문제를 보는 방법|
|Pain Point|사용자가 불편을 느끼는 지점|
|MVP|가장 작은 해결책으로 검증하는 방식|
|Scope Control|이번에 할 것과 하지 않을 것을 나누는 능력|
|Requirement Triage|요구사항의 우선순위를 분류하는 방법|
|YAGNI|지금 필요하지 않은 기능은 만들지 않는 원칙|
|UX Design|사용자의 경험 관점에서 문제를 보는 방식|
|Systems Thinking|문제를 부분이 아니라 흐름과 구조로 보는 사고|

## 주의할 점

Problem Framing은 “사용자의 요청을 무시하자”는 뜻이 아니다.

사용자의 요청을 존중하되, 그 요청이 나오게 된 배경을 더 정확히 이해하자는 뜻이다.

또한 근본 원인만 찾겠다고 너무 오래 분석하면 실행이 늦어질 수 있다.

따라서 적절한 균형이 필요하다.

> 너무 빨리 만들면 잘못된 문제를 풀 수 있고,  
> 너무 오래 분석하면 아무것도 만들지 못할 수 있다.

좋은 Problem Framing은 분석만 하는 것이 아니라, 더 나은 첫 번째 해결책을 고르기 위한 과정이다.

## 내 언어로 다시 설명

Problem Framing은 “무엇을 만들까?”보다 먼저,

> “이걸 어떤 문제로 봐야 하지?”

를 정하는 것이다.

사용자가 말한 요청은 문제 그 자체가 아니라, 사용자가 생각한 해결책일 수 있다.

그래서 바로 구현하기 전에,

> “왜 이 기능이 필요하다고 느꼈을까?”  
> “다른 문제로 볼 수는 없을까?”  
> “더 작고 안전한 해결책은 없을까?”

를 생각해야 한다.

AI 시대에는 특히 중요하다.

AI는 내가 준 요청을 빠르게 구현하지만, 내가 문제를 잘못 잡으면 AI도 그 잘못된 프레임 안에서만 답을 만든다.

따라서 Problem Framing은 AI에게 코드를 시키기 전에, 문제 공간을 먼저 넓히는 과정이다.
