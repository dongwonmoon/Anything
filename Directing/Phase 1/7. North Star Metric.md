## 한 줄 정의

> **서비스가 장기적으로 잘 되고 있는지를 보여주는 가장 핵심적인 지표**

기능 추가/개선이 아니라, 그보다 메타적인 이유. 그 기능을 만들게 된 이유가 해결되었는가?

---

## 왜 중요할까?

표면적으로 보면, 서비스가 얼마나 좋아졌는지 **측정 가능하도록** 만들어주는 역할일 것 같다.

>좋은 Success Metric
>{누가} {어떤 행동/결과}를 {얼마나} 개선했는가?
>회원가입 시작 사용자 중 가입 완료 비율이 45%에서 60%로 증가한다.
>FAQ 도입 후 같은 유형의 반복 문의가 20% 감소한다.
>
>기능이 아니라, 해결하려는 문제를 측정
>숫자나 관찰 가능한 결과로 확인 가능해야 함
>이전 상태와 이후 상태를 비교 가능해야 함
>지표만 좋아지고 사용성이 나빠지는 부작용을 관리해야 함
>핵심 지표가 너무 많지 않음

조금 더 메타적인 이유를 생각해보자면,
"근본적인 문제를 놓치지 않았는지" 확인시켜주는 역할도 있지 않을까??

---

## Leading Metric과 Lagging Metric

#### Leading Metric

먼저 움직이는 지표
문제가 좋아지고 있는지 빠르게 알 수 있음

>비밀번호 입력 오류율
>FAQ 검색 성공률
>검색 결과 클릭률
>이메일 인증 완료율

#### Lagging Metric

나중에 결과로 나타나는 지표

>전체 가입 완료율
>고객 문의 수 감소
>매출 증가
>재방문율 증가

둘 다 중요하지만, 처음 개선할 때는 **Leading Metric**이 **빠르게 피드백을 받을 수 있기 때문에** 더 유용할 때가 많음.

---

## 주의할 점

Success Metric을 잘못 잡으면 지표에만 집중하게 됨.

예시:
```
FAQ 조회수를 늘리자.
```

FAQ 조회수가 늘어난다고 사용자가 더 편해졌다는 뜻 일까?
더 불편해졌다는 뜻이 아닐까?

좋은 예시:
```
FAQ를 본 뒤 같은 주제로 문의하는 비율이 감소한다.
```

## AI에게 시킬 프롬프트

```
이 기능의 Success Metric을 설계해줘.

단순히 기능이 완성됐는지가 아니라,
실제로 문제가 해결됐는지 확인할 수 있는 지표를 제안해줘.

다음 항목으로 나눠줘.

1. 해결하려는 문제
2. 기능 완료 기준
3. 진짜 성공 기준
4. Leading Metric
5. Lagging Metric
6. 잘못 잡기 쉬운 허상 지표
7. 지표가 좋아져도 생길 수 있는 부작용
8. 최소 1차 측정 방법
```

```
핵심 지표:
- 원하는 문서까지 도달하는 시간 감소

보조 지표:
- 첫 페이지 클릭률 증가
- 검색어 재입력 횟수 감소
- 클릭 없는 이탈률 감소

부작용 감시 지표:
- 잘못된 문서 클릭 후 바로 뒤로가기 비율
- 검색 결과 클릭 후 고객 문의율
```

이런식으로 달라고 해도 좋겠다.

## 간단한 예시

#### 회원가입 비밀번호 Pain Point와 연결

문제:
```
사용자가 비밀번호 조건을 나중에 알게 되어 재입력을 반복하고, 가입 과정에서 피로감을 느낀다.
```

가능한 Success Metric:
```
비밀번호 입력 오류율 감소
비밀번호 단계에서의 이탈률 감소
비밀번호 입력 완료까지 걸리는 시간
감소가입 완료율
증가고객문의 중 비밀번호 관련 문의 감소
```

가장 직접적인 지표:
```
비밀번호 입력 오류율
비밀번호 입력 단계 이탈률
```
