## 한 줄 정의

> **문제를 검증하기 위해 가장 작게 만든 첫 번째 해결책**

흔히 **최소 기능 제품**이라고 번역하지만, 더 정확히는:
> 최소한으로 만들어서, 진짜 문제가 맞는지 검증하는 것

---

## 왜 중요할까?

가설 검증에 부가 기능은 필요없다.
필요한 것만 만들어서 빠르게 검증하고,
학습을 하는데 큰 의미가 있다.

---

## MVP의 핵심 질문

```
1. 지금 검증하려는 가설은 무엇인가?
2. 이 가설을 확인하는 데 꼭 필요한 기능은 무엇인가?
3. 없어도 검증 가능한 기능은 무엇인가?
4. 너무 작게 만들어서 검증이 안 되는 건 아닌가?
5. 너무 크게 만들어서 시간이 낭비되는 건 아닌가?
```

가장 중요한 질문은:
> 이걸 만들면 무엇을 배울 수 있지?

MVP는 **학습 장치**다.

---

## 주의할 점

MVP는 **그냥 허접하게 만든 버전이 아님**
나쁜 MVP 이해:

``` text
일단 대충 만든다.
기능을 최대한 적게 만든다.
디자인은 필요 없다.
품질도 낮아도 된다.
```

좋은 MVP 이해:

```
핵심 가설을 검증하는 데 필요한 만큼만 만든다.
가장 중요한 사용자 흐름은 작동해야 한다.
불필요한 기능은 빼지만, 검증에 필요한 품질은 지킨다.
```

("적게"에 포커스를 맞추는 게 아니라 "필요한 것"에 포커스구나.)

즉, MVP는 **작지만 의미있는 것**

---

## AI에게 시킬 프롬프트

```
이 기능 요청을 MVP 관점에서 줄여줘.

다음 항목으로 정리해줘.

1. 검증하려는 핵심 가설
2. 사용자의 Job
3. 반드시 포함해야 하는 최소 기능
4. 이번 MVP에서 제외할 기능
5. 너무 작게 만들면 검증이 안 되는 부분
6. 너무 크게 만들면 낭비되는 부분
7. MVP 성공 기준
8. 다음 버전에서 추가할 후보
```

## 간단한 예시

#### 관리자 페이지 요청

> 관리자 페이지가 필요해요. 악성 게시글이 가끔 올라와서요.

거대한 버전:

```
관리자 로그인
관리자 대시보드
회원 관리
게시글 관리
댓글 관리
신고 관리
통계
권한 관리
감사 로그
운영자별 권한
엑셀 다운로드
검색/필터
```

MVP:

```
관리자가 특정 게시글을 숨김 처리할 수 있다.
숨김 처리된 게시글은 일반 사용자에게 보이지 않는다.
관리자는 숨김 사유를 남긴다.
```

왜냐하면, 진짜 검증하고 싶은 건:
> 운영자가 악성 게시글 노출을 줄일 수 있는가?

(Problem Framing과 RCA가 잘 되어야겠군.)

## 내 언어로 다시 설명

MVP는 조금만 만드는 것이 아니다. 필요한 것만 만드는 것이다.
실효성 반드시 따져야하고, 배우겠다는 집념으로 해야한다.
