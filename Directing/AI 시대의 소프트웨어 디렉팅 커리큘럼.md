> 목표: 직접 코드를 많이 작성하지 않더라도, AI가 만든 소프트웨어 결과물을 더 넓게 진단하고, 더 정확하게 지시하고, 더 책임 있게 검증할 수 있는 감각을 기른다.

---

# 0. 이 커리큘럼의 핵심 관점

이 커리큘럼은 전통적인 개발자 커리큘럼이 아니다.

전통적인 흐름은 보통 다음과 같다.

```text
문법 → 자료구조 → 프레임워크 → 프로젝트 → 설계 → 운영
```

하지만 AI 시대에 내가 기르고 싶은 능력은 다음 흐름에 가깝다.

```text
문제 정의 → 요구사항 → 제약조건 → 데이터 흐름 → 실패 모드 → 위험 감지 → AI 지시 → 결과 검증 → 운영 책임
```

즉, 목표는 “코드를 잘 치는 사람”이 아니라,

> AI가 코드를 생성하더라도  
> 무엇을 만들지, 무엇을 만들지 말지, 무엇이 위험한지, 무엇을 검증해야 하는지 "자연어로" 판단할 수 있는 사람

이 되는 것이다.

---

# 1. 최종 목표

이 커리큘럼을 오래 공부하면 다음 능력을 기르는 것을 목표로 한다.

| 능력 | 의미 |
|---|---|
| 문제 정의력 | 진짜 해결해야 할 문제를 찾는 능력 |
| 판단력 | 지금 중요한 것과 나중에 해도 되는 것을 구분하는 능력 |
| 절제력 | AI가 과하게 만들지 못하게 막는 능력 |
| 의심력 | 그럴듯한 결과를 검증하는 능력 |
| 구조화 능력 | 복잡한 문제를 작은 작업과 검증 단위로 나누는 능력 |
| 책임감 | 배포 후 사용자, 데이터, 비용, 장애까지 고려하는 능력 |
| 설명력 | 사람과 AI 모두에게 명확하게 지시하고 설명하는 능력 |
| 위험 감지 | 나중에 터질 문제를 미리 보는 능력 |
| 균형감 | 품질, 속도, 비용, 복잡도 사이에서 선택하는 능력 |
| 맥락 이해 | 기술보다 업무 목적과 사용자 상황을 먼저 보는 능력 |

# 2. 공부 방식

## 2.1 원칙

이 커리큘럼은 암기용이 아니다.

개념을 하나 배울 때마다 다음 질문으로 연결한다.

```text
이 개념을 알면 AI에게 어떤 더 좋은 질문을 던질 수 있는가?
```

---

## 2.2 매 개념마다 만들 노트

각 개념은 아래 형식으로 정리한다.

```markdown
# 개념명

## 한 줄 정의

## 언제 떠올릴까?

## 이 개념을 모르면 생길 수 있는 문제

## 대표 질문

## AI에게 시킬 프롬프트

## 간단한 예시

## 관련 개념

## 내 언어로 다시 설명
```

## 2.3 매 기능마다 만들 분석 문서

```markdown
## 1. 이 기능의 진짜 목적

## 2. 사용자 흐름

## 5. 상태 변화

## 6. 실패 케이스

## 9. 동시성 위험

## 12. AI에게 맡길 작업 단위

## 13. AI 결과물 검수 체크리스트
```

- 엑셀 업로드

# 3. 전체 로드맵

## Phase 1. 문제를 정확히 정의하는 능력

목표:

> AI에게 바로 구현을 맡기기 전에, 무엇을 왜 만들어야 하는지 분명히 정의한다.

배울 것:

| 주제 | 핵심 |
|---|---|
| Problem Framing | 문제를 어떤 틀로 볼 것인가 |
| Root Cause Analysis | 증상과 원인을 구분 |
| 5 Whys | 왜 그런지 반복해서 파고들기 |
| Jobs To Be Done | 사용자가 진짜 하려는 일 |
| User Journey | 사용자의 실제 흐름 |
| Pain Point | 사용자의 불편 지점 |
| Success Metric | 성공 기준 |
| North Star Metric | 서비스 핵심 지표 |
| MVP | 최소 기능으로 검증 |
| Scope Control | 범위 조절 |
| Requirement Triage | 요구사항 우선순위 분류 |

핵심 질문:

```text
우리가 지금 만들려는 것은 진짜 필요한가?
이 기능이 해결하려는 문제는 무엇인가?
사용자가 실제로 원하는 결과는 무엇인가?
성공했다는 것을 어떻게 판단할 것인가?
이번 버전에서 하지 않아도 되는 것은 무엇인가?
```

AI 프롬프트:

```text
내가 제시한 기능 요청을 그대로 구현하지 마.

먼저 아래 항목으로 나눠 분석해줘.

1. 진짜 문제
2. 겉으로 드러난 증상
3. 사용자의 실제 목적
4. 이 기능이 없어도 되는 경우
5. 성공 기준
6. 이번 버전에서 제외해야 할 범위
7. 내가 잘못 문제를 정의했을 가능성
```

실습:

```text
“예약 시스템을 만들어줘”라는 요청을 받아서,
진짜 문제, 사용자, 성공 기준, 제외 범위, 1차 MVP로 나눠 정리한다.
```

# 4. Phase 2. 요구사항을 구조화하는 능력

목표:

> 자연어를 그냥 말하는 것이 아니라, AI가 오해하지 않도록 구조화된 명세로 바꾼다.

배울 것:

| 주제 | 핵심 |
|---|---|
| Functional Requirement | 기능 요구사항 |
| Non-functional Requirement | 성능, 보안, 안정성 요구사항 |
| Acceptance Criteria | 완료 기준 |
| User Story | 사용자 관점의 요구 |
| Use Case | 구체적 사용 시나리오 |
| Business Rule | 업무 규칙 |
| Constraint | 제약 조건 |
| Out of Scope | 제외 범위 |
| Assumption | 전제 조건 |
| Dependency | 의존 대상 |
| Definition of Done | 완료 정의 |

핵심 질문:

```text
무엇을 해야 하는가?
무엇을 하지 않아야 하는가?
정상 케이스는 무엇인가?
실패 케이스는 무엇인가?
완성됐다고 볼 기준은 무엇인가?
성능, 보안, 권한, 운영 요구사항이 빠지지 않았는가?
```

AI 프롬프트:

```text
아래 기능 요청을 요구사항 명세로 바꿔줘.

반드시 다음 항목으로 나눠줘.

1. 기능 요구사항
2. 비기능 요구사항
3. 정상 시나리오
4. 실패 시나리오
5. 예외 케이스
6. 제외 범위
7. 전제 조건
8. 수용 기준
9. 모호한 부분
10. 추가로 확인해야 할 질문
```

실습:

```text
“회원가입 기능”을 코드 없이 요구사항 명세로 작성한다.
단, 소셜 로그인, 관리자 승인, 이메일 인증은 제외할지 포함할지 직접 판단한다.
```

# 5. Phase 3. 범위를 줄이는 능력

목표:

> AI가 많이 만들 수 있을수록, 오히려 덜 만들 수 있는 판단력을 기른다.

배울 것:

| 주제 | 핵심 |
|---|---|
| YAGNI | 지금 필요하지 않으면 만들지 않기 |
| KISS | 단순하게 유지하기 |
| MVP | 최소 제품 |
| MoSCoW Prioritization | Must, Should, Could, Won’t |
| Opportunity Cost | 하나를 하면 다른 것을 못 하는 비용 |
| Over-engineering | 과한 설계 |
| Under-engineering | 부족한 설계 |
| Scope Creep | 범위가 계속 늘어나는 문제 |

핵심 질문:

```text
이 기능은 지금 꼭 필요한가?
나중에 필요할 수 있다는 이유만으로 만들고 있지 않은가?
이 복잡도는 현재 규모에 맞는가?
AI가 과하게 만든 것은 아닌가?
이번 버전에서 제외해야 할 것은 무엇인가?
```

AI 프롬프트:

```text
이 요구사항을 보고 과한 부분을 찾아줘.

다음 기준으로 분류해줘.

1. 반드시 필요한 기능
2. 있으면 좋지만 나중에 해도 되는 기능
3. 지금 만들면 복잡도만 늘어나는 기능
4. 명확히 제외해야 할 기능
5. 나중에 다시 검토할 조건
```

실습:

```text
쇼핑몰 기능 30개를 적고,
1차 출시, 2차 출시, 보류, 폐기로 분류한다.
```

# 6. Phase 4. 시스템 흐름을 읽는 능력

목표:

> 기능을 코드 덩어리로 보지 않고, 입력과 처리와 출력의 흐름으로 본다.

배울 것:

| 주제 | 핵심 |
|---|---|
| Input → Process → Output | 입력, 처리, 출력 |
| Data Flow | 데이터 흐름 |
| Control Flow | 제어 흐름 |
| Pipeline | 단계별 처리 |
| Fan-out | 작업을 여러 갈래로 나눔 |
| Fan-in | 여러 결과를 다시 모음 |
| Queue | 대기열 |
| Worker Pool | 작업자 풀 |
| Batch Processing | 묶음 처리 |
| Streaming | 실시간 흐름 처리 |
| Event-driven Architecture | 이벤트 중심 구조 |
| Pub/Sub | 발행/구독 구조 |
| Synchronous Processing | 동기 처리 |
| Asynchronous Processing | 비동기 처리 |
| Pull Model | 가져오는 방식 |
| Push Model | 밀어넣는 방식 |
| Backpressure | 처리량 제어 |

핵심 질문:

```text
작업은 어디서 들어와서 어디로 나가는가?
순차 처리해야 하는가?
나눠서 동시에 처리할 수 있는가?
나눈 결과를 다시 모을 때 병목은 없는가?
입력 속도가 처리 속도보다 빠르면 어떻게 되는가?
실패한 작업은 어디로 가는가?
```

AI 프롬프트:

```text
이 기능을 데이터 흐름 관점에서 분석해줘.

다음 항목을 포함해줘.

1. 입력
2. 처리 단계
3. 출력
4. 외부 의존성
5. 순차 처리 지점
6. 병렬 처리 가능한 지점
7. fan-out 가능 지점
8. fan-in 병목 위험
9. 큐가 필요한지 여부
10. backpressure가 필요한 상황
11. 실패한 작업의 처리 방식
```

실습:

```text
대량 이메일 발송 기능을 분석한다.

- 순차 발송하면 어떤 문제가 있는가?
- fan-out으로 나누면 어떤 장점이 있는가?
- fan-in으로 결과를 모을 때 무엇을 저장해야 하는가?
- 실패한 이메일은 어떻게 재시도해야 하는가?
```

# 7. Phase 5. 성능과 병목을 보는 능력

목표:

> “느리다”를 막연하게 보지 않고, 병목의 종류를 구분한다.

배울 것:

| 주제 | 핵심 |
|---|---|
| Latency | 한 요청의 응답 시간 |
| Throughput | 단위 시간당 처리량 |
| Bottleneck | 전체 성능을 제한하는 지점 |
| Amdahl’s Law | 병렬화의 한계 |
| Little’s Law | 대기열, 처리량, 대기시간 관계 |
| CPU-bound | CPU 계산 병목 |
| I/O-bound | 파일, DB, 네트워크 병목 |
| N+1 Query | DB 조회 폭증 |
| Index | 검색 최적화 |
| Caching | 반복 조회 줄이기 |
| Cache Invalidation | 캐시 갱신 문제 |
| Rate Limit | 호출량 제한 |
| Pagination | 데이터 나눠 가져오기 |
| Lazy Loading | 필요할 때 불러오기 |
| Eager Loading | 미리 불러오기 |
| Profiling | 실제 병목 측정 |
| Benchmarking | 비교 측정 |

핵심 질문:

```text
한 요청이 느린가, 전체 처리량이 낮은가?
느린 지점을 측정했는가?
DB가 느린가?
네트워크가 느린가?
외부 API가 느린가?
CPU 계산이 문제인가?
I/O 대기가 문제인가?
캐시가 도움이 되는 문제인가?
병렬 처리하면 오히려 다른 곳이 터지지 않는가?
```

AI 프롬프트:

```text
이 성능 문제를 추측으로 고치지 마.

가능한 원인을 다음 관점으로 분류해줘.

1. latency 문제
2. throughput 문제
3. 알고리즘 복잡도
4. DB 쿼리
5. 인덱스
6. 네트워크
7. 외부 API
8. CPU 병목
9. I/O 병목
10. 캐시 가능성
11. fan-out/fan-in 가능성
12. rate limit 위험
13. 측정해야 할 지표
14. 잘못 개선했을 때의 부작용
```

실습:

```text
“이미지 1,000장을 처리하는 기능이 느리다”는 상황을 두고,
가능한 병목을 10개 이상 가정하고 각각 확인 방법을 작성한다.
```

# 8. Phase 6. 데이터와 상태를 다루는 능력

목표:

> 시스템의 많은 문제는 코드가 아니라 데이터의 의미와 상태 변화에서 발생한다는 것을 이해한다.

배울 것:

| 주제 | 핵심 |
|---|---|
| Entity | 핵심 데이터 객체 |
| Relationship | 데이터 관계 |
| ERD | 데이터 구조도 |
| Normalization | 정규화 |
| Denormalization | 비정규화 |
| Primary Key | 기본키 |
| Foreign Key | 외래키 |
| Unique Constraint | 중복 방지 |
| Transaction | 작업 단위 보장 |
| ACID | 트랜잭션 안정성 |
| State Machine | 상태 전이 |
| Audit Log | 변경 이력 |
| Soft Delete | 삭제 표시 |
| Hard Delete | 실제 삭제 |
| Immutable Data | 변경 불가 데이터 |
| Versioning | 버전 관리 |
| Snapshot | 특정 시점 저장 |
| Event Sourcing | 이벤트 이력 기반 상태 관리 |

핵심 질문:

```text
이 데이터는 무엇을 의미하는가?
이 값은 바뀌는가, 바뀌면 안 되는가?
과거 이력이 필요한가?
삭제하면 관련 데이터는 어떻게 되는가?
동시에 수정하면 안전한가?
주문 당시 가격처럼 스냅샷이 필요한가?
상태는 어떤 순서로 바뀌어야 하는가?
```

AI 프롬프트:

```text
이 기능에서 필요한 데이터를 모델링해줘.

다음 항목을 포함해줘.

1. 핵심 엔티티
```

| Leaky Abstraction | 추상화는 언젠가 새어 나옴 |

| Gall’s Law | 복잡한 시스템은 단순한 시스템에서 진화해야 함 |
| Chesterton’s Fence | 없애기 전에 왜 있는지 이해해야 함 |
| Goodhart’s Law | 지표가 목표가 되면 망가짐 |
| Hyrum’s Law | 충분히 많은 사용자가 있으면 모든 동작에 의존하게 됨 |
| Postel’s Law | 받을 때 관대하고 보낼 때 엄격하라 |
| Murphy’s Law | 잘못될 수 있는 것은 잘못될 수 있음 |

핵심 질문:

```text
이 문제를 다른 법칙으로 보면 어떤 위험이 보이는가?
지표가 본질을 왜곡하고 있지 않은가?
기존 구조를 없애기 전에 이유를 이해했는가?
복잡한 시스템을 처음부터 만들고 있지 않은가?
병렬화해도 전체 성능이 크게 개선되지 않는 지점은 없는가?
```

AI 프롬프트:

```text
이 설계를 고전적인 소프트웨어 법칙 관점에서 검토해줘.

다음 개념과 연결해서 위험을 설명해줘.

1. Conway’s Law
2. Gall’s Law
3. Goodhart’s Law
4. Chesterton’s Fence
5. Amdahl’s Law
6. Hyrum’s Law
7. Leaky Abstraction
8. Murphy’s Law
```

실습:

```text

- 누가 의존하고 있을까?
```

# 33. 앞으로의 공부 방향

이 커리큘럼은 한 번에 끝내는 것이 아니다.

개념 하나를 배울 때마다 다음을 남긴다.

```text
이 개념을 알기 전에는 어떤 질문을 못 했는가?
이 개념을 알고 나니 AI에게 어떤 질문을 새로 할 수 있는가?
이 개념이 실제 기능에서 어떤 실패를 막아주는가?
```

궁극적으로 목표는 이것이다.

> AI에게 더 많은 코드를 만들게 하는 사람이 아니라,  
> AI가 더 넓고 안전한 문제 공간을 보게 만드는 사람이 되는 것.
